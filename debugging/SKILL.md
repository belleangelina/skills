# debugging

定位、修复 bug 时使用。

## 核心原则

不要猜，不要一上来就改代码。

先找到根因，再做最小修复，最后给出可执行的验证方案。

## 调试流程

### 1. 确认问题

先明确：

* 期望行为是什么？
* 实际行为是什么？

完整阅读相关错误信息、日志、代码改动、配置和硬件背景。

### 2. 复现问题

尽量找到稳定复现方式：

* 哪个版本、配置或操作步骤会触发？
* 是否每次都会发生？
* 需要什么硬件条件或外部输入？

如果不能稳定复现，尽可能多地收集证据。

### 3. 定位根因

从出错点往上追：

* 坏数据或异常状态从哪里来？
* 哪一层开始变错？
* 最近代码、配置或硬件条件是否变化？
* 有没有正常实现可以对比？

目标是找出“为什么会坏”，而不只是“哪里报错”。

### 4. 验证假设

一次只提出一个可验证的假设：

> 我认为问题是 X，因为 Y。

然后用最小实验验证它，例如检查日志、变量、寄存器、信号或最小复现固件。不要一次性改很多地方。

### 5. 最小修复

确认根因后，只修真正原因：

* 不做无关重构
* 不顺手优化
* 不引入不必要依赖
* 不随意改变时序
* 尽量保持现有行为不变

### 6. 验证修复

#### 通用软件 bug

**对于通用软件，Agent 应尽可能自行验证。实现闭环：`修复->部署->验证->再修复`，直到解决问题。必要时才让用户协助。**

#### 嵌入式软件 bug

**嵌入式场景下，Agent 可能难以直接访问真实硬件，需要用户协助完成目标板验证。**

修复后应提供：

* Agent 可以完成的软件侧检查；
* 用户需要在目标板上执行的验证步骤；
* 明确的观测方式和通过标准；
* 必要的回归测试范围。

最终结论必须区分：

* 已由 Agent 验证的内容；
* 只能通过静态分析推断的内容；
* 仍需用户在硬件上确认的内容。

如果修复失败，不要继续叠补丁；回到根因调查。

## 输出要求

最终回答应包含：

* **根因**：真正的问题是什么。
* **修复**：改了什么，为什么这样改。
* **验证方案**：软件侧怎么检查，硬件侧怎么确认。
* **待确认项**：哪些仍需用户在目标板上确认。
* **风险/备注**：可能影响哪些已有功能或硬件行为。

## 红线

不要做这些事：

* 没查明原因就修。
* 凭直觉试 patch。
* 一次改多个无关地方。
* 只修症状不修源头。
* 多次失败后继续盲试。
