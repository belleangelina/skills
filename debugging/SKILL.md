# debugging

定位、修复 bug 时使用。

## 核心原则

先检查与故障相关的证据，再决定修改。允许提出待验证的假设，但不要把假设当作已确认根因。

用证据定位原因，做最小修复，并完成当前环境和任务授权范围内的验证。流程按问题复杂度裁剪，明显的小问题不必机械执行每一步。

## 调试流程

### 1. 确认问题

先明确：

* 期望行为是什么？
* 实际行为是什么？

聚焦阅读相关错误信息、日志、代码改动和配置；涉及硬件时再检查硬件背景。能够自行查明的信息先自行查明，只询问影响判断且确实缺失的信息。

### 2. 复现问题

尽量找到稳定复现方式：

* 哪个版本、配置或操作步骤会触发？
* 是否每次都会发生？
* 需要什么硬件条件或外部输入？

如果不能稳定复现，优先收集能够区分候选原因的证据；避免无目标地扩大日志和调查范围。

### 3. 定位根因

从出错点往上追：

* 坏数据或异常状态从哪里来？
* 哪一层开始变错？
* 最近代码、配置或硬件条件是否变化？
* 有没有正常实现可以对比？

目标是找出“为什么会坏”，而不只是“哪里报错”。

### 4. 验证假设

可以列出多个候选原因，按证据和验证成本排序，再选择最有区分力的实验：

> 我认为问题是 X，因为 Y。

然后用最小实验验证它，例如检查日志、变量、寄存器、信号或最小复现固件。不要一次性改很多地方。

### 5. 最小修复

有足够证据支持原因后实施针对性修复；诊断性改动应可撤销，并与最终修复区分：

* 不做无关重构
* 不顺手优化
* 不引入不必要依赖
* 不随意改变时序
* 保持修复目标之外的行为不变

### 6. 验证修复

按实际访问能力决定验证责任，不按“通用软件/嵌入式”预设是否需要用户协助。

- 自行完成可执行的构建、测试、复现和必要回归；验证范围与改动影响相称。
- 已具备目标设备的 SSH、串口或 Web 访问方式，且任务已授权相应验证时，自行完成板端验证；需要远程设备部署流程时使用 `remote-device-validation`。
- 只有缺少必要访问条件、需要物理操作或需要用户作关键决定时才请求协助；同时继续不依赖该条件的工作。
- 部署仅在任务需要且已有授权的范围内执行，不把普通修复自动扩展为发布或设备升级。
- 验证失败时根据新证据调整假设，避免叠加无依据补丁。检查通过后，仅有新改动、失败或未解决风险时才扩大或重复测试。

## 输出要求

简要说明证据支持的根因、实际修改和已执行的验证。明确区分实测结果与静态推断；有阻塞或未验证项时再给出所需协助和通过标准。无需为不适用的硬件待确认项或风险凑固定章节。

## 红线

不要做这些事：

* 没有证据支持就把试探性修改当作最终修复。
* 没有可检验假设就盲目尝试 patch。
* 一次改多个无关地方。
* 只修症状不修源头。
* 多次失败后继续盲试。
