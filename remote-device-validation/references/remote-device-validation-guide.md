# 远程设备验证泛化流程

## 目的

本文沉淀远程验证真实嵌入式设备时可复用的流程、部署方式、问题闭环和踩坑处理方法。

本文只保存流程规则，不保存具体设备 IP、账号、密码、测试 SSID、SIM 卡号等输入内容。具体输入复用当前会话已明确的信息；状态变更前仍读取已有项目输入清单以合并设备限制，不重复向用户索要已明确的信息。

功能专项文档只需要补充以下内容：

- 当前功能的测试账号、测试数据和专项参数。
- 当前功能的专项日志过滤命令。
- 当前功能的测试用例和阶段记录。
- 当前功能特有的风险、不可触碰状态和现场配合项。

## 执行前提

执行前检查本轮动作所需的信息。部署、重启、网络调整或其他状态变更前，读取已有的用户指定输入文件；未指定时检查并读取默认文件。即使会话信息足够，也要合并文件中的设备限制和恢复条件：

```text
docs/remote-device-validation-inputs.md
```

输入文件应记录：

- 设备访问方式。
- SSH、Web、串口信息。
- OTA 页面入口、上传接口、表单字段和失败恢复方式。
- 本轮任务范围、已有授权和操作限制。
- 现场物理配合。

文件不存在且会话已有所需信息时可继续；已读取且无变化迹象的同一文件无需逐条命令重读。一般操作请求不视为取消文件中的具体限制，用户未明确覆盖的冲突需要澄清。仅当本轮动作必需的信息缺失、冲突或有证据表明过期时，暂停依赖该信息的动作并询问；继续其他已授权且不受影响的工作。只读检查不要求 OTA 或恢复清单齐全。

用户已要求设备部署或远程自循环验证时，可继续其范围内必要的 OTA、SSH 临时替换、重启、临时网络调整和本轮测试数据清理，遵守已有授权与限制，不逐项重复确认。规划或只读检查不自动授权这些变更；技能不扩展任务范围。

如需破坏性验证，必须确认现场可恢复，例如断电重启、恢复网络、重刷固件或重新插拔外设。

开始远程动作前，输入文件至少要能回答以下问题：

- 当前远程访问依赖哪个网络接口、路由和 DNS。
- 如果本轮验证会改动网络，是否有备用访问方式或现场恢复动作。
- OTA 上传成功后文件落到哪里，升级由哪个脚本或服务执行。
- 本轮构建产物能覆盖哪些目录或分区，明确不能覆盖哪些目录或分区。
- 设备升级或重启后预计多久恢复 SSH/Web。
- 失败时先远程排查还是立即要求现场介入。

如果这些信息缺失且本轮动作依赖它们，应先补齐，不能边升级边猜恢复路径。

## 专项日志

专项文档应给出当前功能需要关注的日志过滤命令，例如：

```sh
logcat | grep -Ei '<feature>|<process>|error|fail'
dmesg | grep -Ei '<driver>|<device>|error|fail'
```

日志命令要尽量聚焦。不要把完整 `logcat`、完整 `dmesg`、完整构建流水或大量远端输出写入对话上下文。完整日志优先重定向到 `/tmp/*.log`，对话中只保留退出状态、关键错误、相关片段和必要尾部日志。

凭据和敏感数据处理规则：

- 不要把真实密码、token、SIM 卡号、测试账号等写入 skill、模板或通用 reference。
- 远程命令中尽量通过环境变量或临时 askpass 脚本传递密码，不把密码写入命令历史、日志或仓库文件。
- 对话和验证记录只保留必要摘要；需要展示命令时，用占位符替代敏感值。
- 临时凭据文件应放在 `/tmp`，权限收紧，验证结束后清理。

## 建立基线

每轮远程验证开始前，先采集设备基础状态：

```sh
uname -a
ifconfig
ip route
cat /etc/resolv.conf
ps
```

然后根据专项文档追加功能日志和状态命令。

基线要确认：

- 设备当前版本是否是预期版本。
- 目标进程和依赖服务是否正常运行。
- 网络、路由和 DNS 是否支持远程继续操作。
- 关键配置文件是否处于预期状态。
- 当前问题是否能稳定复现。

如果远程验证可能改动网络、路由、DNS、无线连接、蜂窝数据或防火墙规则，应先确认不会切断当前远程访问路径，或准备可恢复的备用访问方式。

## 自循环验证闭环

发现问题或实现新功能后的处理顺序：

1. 保存复现步骤、接口请求、页面状态、板端日志和当前设备状态。
2. 判断问题归属到页面、Web API、业务服务、底层驱动、系统配置或部署流程。
3. 修改代码或配置。
4. 本地构建，并检查真实退出码。
5. 按改动范围选择部署方式。
6. 部署到设备并等待设备恢复访问。
7. 确认新版本实际生效，例如版本、文件 MD5、进程加载路径、页面资源或接口返回。
8. 复测原问题。
9. 回归该功能的核心流程。
10. 记录本轮结论、残留风险和下一轮动作。
11. 如果仍失败，基于新证据继续修改并进入下一轮，直到验证通过、用户要求停止，或遇到无法绕过的外部阻塞。
12. 验证结束前做收尾，恢复临时状态并记录最终设备状态。

每轮记录必须包括：

- 本轮目标。
- 构建产物和真实构建结果。
- 部署方式。
- 设备恢复状态。
- 关键命令和关键输出摘要。
- 通过、失败或阻塞结论。

收尾至少确认：

- 临时后台 `cat`、`tail`、日志采集或测试进程已停止。
- 临时修改的网络、路由、DNS、接口状态已按预期恢复或记录为目标状态。
- 临时 remount 的根分区或其他分区已恢复项目要求的读写状态。
- 敏感临时文件、askpass 脚本和大日志文件已清理，或记录了保留原因。
- 设备最终运行版本、目标服务状态和远程访问状态明确。

## Core 与数据库排查

远程接口返回空响应、目标进程退出或设备重启时，先固定证据再修改代码：

- 记录复现请求、触发时间、进程 PID 和 core 列表；对比触发前后的最新 core，避免分析旧文件。
- core 在 /data/log/ 目录，拉取大 core 时优先在板端压缩再传输，压缩很慢时用文件大小和远端进程状态确认仍在前进。
- 本地构建后保留与部署二进制 BuildID 一致的未 strip 符号文件；调试前比较板端目标文件 MD5 或 BuildID，确认 core、rootfs 和符号来自同一轮产物。
- 使用对应交叉 gdb，设置 `sysroot` 和 `solib-search-path` 到本轮 rootfs；完整 `thread apply all bt full` 写入 `/tmp/*.log`，对话只摘出崩溃线程、业务线程和关键请求。
- 不要只看当前线程 `SIGILL`、`abort` 或 libc 顶层帧就下结论；要沿业务线程栈找到具体处理函数、源码行和入参。
- 如果 gdb 缺少宿主库，优先安装兼容库；无法安装时可临时解包 `.deb` 并用 `LD_LIBRARY_PATH` 只影响当前 gdb 命令。
- 牵涉数据库时，在板端用 `sqlite3` 检查实际库文件、`PRAGMA table_info(<table>)`、计数和关键行；不要假设结构体字段、导入表头或历史代码一定匹配当前表结构。
- 修复后先复测最小复现请求，再检查 PID、core 列表和关键 DB 行，确认没有新增崩溃和测试数据已清理。

## 部署方式选择

根据本次修改范围选择部署方式：

- 只修改 `/opt/aio` 或 Web 页面资源：最终验证优先使用应用轻量升级包，并让设备走正式重启路径。
- 修改 `/usr/lib`、`/usr/bin`、`/etc` 或 rootfs 基础文件：不能默认使用应用轻量升级包，需确认 OTA 包覆盖范围，或通过 SSH 临时替换做探测验证。
- 修改内核、DTS、驱动模块、bootfs 或系统分区：使用对应系统升级包或完整烧录包，并先确认升级配置包含目标分区。

涉及 `aio` 的改动，尤其是 `/opt/aio` 和 `/opt/webpage` 下的文件，优先用应用升级包覆盖 `/opt` 后重启设备验证。通过 SSH 只替换 `/opt/aio` 并只重启 `aio` 进程适合快速探测问题，但不宜作为最终验证结论：它可能绕过真实 OTA 解包流程，旧进程可能没有完全退出，启动脚本、环境变量、资源文件和根分区空间状态也可能与正式升级后不同。

## OTA 包覆盖范围

不要凭文件名推断升级包覆盖范围。每个项目都应在输入清单或专项文档里明确以下信息：

- 轻量应用升级包的文件名格式。
- 系统或网络升级包的文件名格式。
- OTA 上传接口如何识别包类型。
- 包上传成功后写入设备的路径。
- 设备重启后由哪个脚本解包或触发升级。
- 能覆盖哪些目录或分区。
- 明确不能覆盖哪些目录或分区。
- 失败后的恢复方式。

常见规则：

- 应用轻量升级包通常只适合验证 `/opt` 下的应用、页面资源、脚本和配置。
- 系统升级包是否覆盖 rootfs、bootfs、kernel 或其他分区，必须看项目升级配置，不能默认覆盖。
- 完整烧录包适合工厂烧录或现场重刷，不要和 Web OTA 上传包混用。

每轮 OTA 都要确认：

- 升级包是否上传成功。
- OTA 接口或页面是否返回成功。
- 设备是否按预期重启或重启目标进程。
- 升级后 Web 页面和 SSH 是否恢复访问。
- 目标文件、页面资源、配置文件和进程是否变为新版本。
- 升级失败时是否需要停止自动尝试，转为现场恢复。

## Web OTA 自循环验证

如果设备 Web 页面支持 OTA，且已提供登录信息和 OTA 入口，可以按以下方式执行远程升级循环：

1. 本地修改代码。
2. 本地构建，并根据修改范围生成对应升级包。
3. 通过 Web 页面或 OTA 上传接口上传升级包。
4. 触发 OTA 升级。
5. 等待设备升级完成；如果设备自动重启，则等待设备重新上线。
6. 通过 SSH 或串口确认版本、进程、日志和关键状态。
7. 执行专项回归测试。
8. 如果发现问题，继续修改并进入下一轮。

等待设备恢复时要分阶段检查：

- 网络是否可达。
- SSH 是否可登录。
- Web 是否可访问。
- 目标服务是否已启动。
- 升级脚本是否完成清理。

不要把“设备恢复访问”和“新产物 MD5 生效”合并成一个长轮询条件。Web/SSH 已恢复但目标文件 MD5、版本或加载路径仍不匹配时，应立即停止等待并转入 OTA 状态排查，例如检查升级包落盘、校验文件、升级脚本日志和目标文件覆盖结果；继续只等“新 MD5 生效”会掩盖真实失败点。

不要在设备刚断连时立刻判定失败；按输入清单中的预计升级耗时等待。超时后先采集 SSH/Web 恢复情况，再判断是否需要现场介入。

## SSH 临时替换注意事项

通过 SSH 临时替换单个二进制、页面资源或库文件可以减少完整升级次数，但必须确认设备文件系统是否可写：

```sh
mount | grep ' / '
mount -o remount,rw /
```

替换完成后应执行：

```sh
sync
```

如果需要验证正式启动路径，应优先 `reboot`。如果只重启目标进程，必须确认新进程实际加载的是目标文件。例如验证共享库时：

```sh
pidof <process>
cat /proc/<pid>/maps | grep '<library-name>'
```

如果 watchdog 或启动脚本会自动拉起旧环境，仅手动设置 `LD_LIBRARY_PATH` 启动进程不能作为有效验证依据。

临时替换文件时：

- 只备份本轮验证要替换的文件。
- 记录替换前后的 MD5 或大小。
- 重启进程或设备前执行 `sync`。
- 如曾临时 remount 根分区为 `rw`，验证结束前恢复项目要求的挂载状态。

对 `aio` 改动，SSH 临时替换后的进程级重启只作为定位手段。最终仍应尽量回到应用升级包加设备重启的路径，确认正式升级流程、启动脚本和 `/opt` 资源整体状态都符合预期。

如果验证过程中改动了网络或默认路由，不能只看目标接口是否联网；还要确认当前远程访问路径没有被误切走，必要时用 `ip route get <remote-client-ip>` 或等价命令确认回程路径。

## SSH 非交互登录

当前环境没有 `sshpass` 时，可以用 OpenSSH 的 `SSH_ASKPASS` 完成一次性非交互登录。关键点是密码变量必须 `export`，否则 askpass 子进程读不到密码，会表现为密码正确但连续认证失败。

推荐模板：

```sh
cat > /tmp/remote_askpass.sh <<'EOF'
#!/bin/sh
printf '%s\n' "$REMOTE_SSH_PASSWORD"
EOF
chmod 700 /tmp/remote_askpass.sh

export REMOTE_SSH_PASSWORD='<ssh-password>'
DISPLAY=none \
SSH_ASKPASS=/tmp/remote_askpass.sh \
SSH_ASKPASS_REQUIRE=force \
setsid ssh -o PreferredAuthentications=password \
    -o PubkeyAuthentication=no \
    -o StrictHostKeyChecking=no \
    -o UserKnownHostsFile=/tmp/remote_known_hosts \
    <user>@<device-ip> '<remote-command>'
```

注意事项：

- 不要把 Web 登录密码当作 SSH 密码尝试，除非用户明确确认两者相同。
- 不要把真实密码写入仓库文件。
- 调试 SSH 失败时可以临时加 `-vv`，但输出中必须过滤认证相关敏感信息。
- 远端提示 `Could not chdir to home directory` 不一定是失败，只要命令退出码为 0 且输出符合预期即可继续。
- 验证结束后删除临时 askpass 脚本，并在当前 shell 中清空敏感环境变量。

## SSH 返回 0 但 stdout 为空

如果 SSH 返回码是 0，但对话里看不到远端 `stdout`，不要马上判断远端命令没有执行。当前工具链下可能出现直接命令输出被采集侧吞掉的情况，表现为 SSH 正常退出，但 stdout 没有回到对话上下文。

排查时把 SSH 调试日志、stdout 和 stderr 都写到 `/tmp`，只查看连接、认证和执行摘要：

```sh
DISPLAY=none \
SSH_ASKPASS=/tmp/remote_askpass.sh \
SSH_ASKPASS_REQUIRE=force \
setsid ssh -vv -o PreferredAuthentications=password \
    -o PubkeyAuthentication=no \
    -o StrictHostKeyChecking=no \
    -o UserKnownHostsFile=/tmp/remote_known_hosts \
    <user>@<device-ip> 'printf "SSH_OK\n"' \
    >/tmp/remote_ssh_probe.out 2>/tmp/remote_ssh_probe.err
status=$?
printf 'SSH_EXIT=%s\n' "$status"
grep -Ei 'authenticated|sending command|exec request|exit status' /tmp/remote_ssh_probe.err
cat /tmp/remote_ssh_probe.out
```

如果日志显示认证成功、远端命令已发送且退出状态为 0，同时 `/tmp/remote_ssh_probe.out` 能看到 `SSH_OK`，说明 SSH 链路正常，问题在输出采集链路。后续远程验证可以把关键输出先重定向到 `/tmp/*.out`，再单独读取文件内容。

## SSH 长命令或启动脚本挂住

不要把停止服务、复制文件、改权限、同步、启动服务、等待、读取状态和 remount 等动作打包成一条很长的 SSH 命令。长命令更难定位失败点，也更容易遇到启动脚本或后台进程继承 SSH 会话 stdout/stderr，导致远端动作已经完成但 SSH 连接不退出。

推荐把远程操作拆成短命令分步执行：

- 一条命令只做一个明确动作，例如停止服务、复制文件、启动服务、读取状态分别执行。
- 可能挂住的动作单独执行，并设置超时或在挂住后中断，再用新的 SSH 短命令读取结果。
- 启动服务后不要在同一条 SSH 中继续串大量检查项；先返回，再单独查询 `pidof`、`md5sum`、日志和接口状态。
- 复杂逻辑优先写入远端 `/tmp/*.sh`，但执行脚本本身仍要控制输出和超时，关键结果写到 `/tmp/*.out` 后再读取。

## 远程工具受限

如果远程 SSH、curl、scp 或 OTA 操作被当前工具环境的网络、审批或用量限制拦截，应立即停止远程闭环验证，不要尝试绕过限制。此时只做三件事：

- 记录已采集到的设备证据和失败结论。
- 转为本地根因分析、代码准备和构建验证。
- 等远程访问恢复后，再继续部署和板端复测。
